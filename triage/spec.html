Triage Core

The decision layer of Triage: one controller on Kubernetes that receives signals from agents, alert providers and people, decides which of them are issues, keeps what it learns as MemoryCells, and tells the right people through channels, a messenger, an API and MCP. Rules, the service graph and recorded patterns decide in the event path; a decision model answers typed questions; a reasoning model reflects a few times a day and never opens an issue.

01

Architecture

The core is one Go binary run as a Kubernetes controller. It reconciles MemoryCell objects, serves the HTTP API with the MCP server on port 8080, runs a second MCP listener on 8083, an events server on 8086 for alert webhooks and the agent WebSocket, an MS Teams connector on 8085, health probes on 8082 and, with several replicas, a gossip mesh on 8088. Nothing is compiled in for the UI; a ui cell names an OCI artifact that the core pulls and serves.

All persistent state is a MemoryCell of the xray.triageagent.dev/v1 kind in the core's namespace: events, issues, knowledge, patterns, the configuration documents the core applies while it runs (policy, prompts, notification routing, the tenant registry and each tenant's service graph) and the counters it keeps (section 7). The chart ships that one CRD. One package, the store, is the only code that reads or writes cells through the Kubernetes client; everything else asks it for a typed document, a memory cell or a claim. Deployment wiring is not a cell: the chart renders it into a file that the core reads once at start (section 14). The state that is only useful while the process runs, such as the event hub, the service ledger, the situation frame and the rate limiters, lives in memory, belongs to one replica and starts empty after a restart.

The agent that runs the event path takes what it needs from the rest of the process at construction, as interfaces it defines: a lease (does this replica hold the leader lease), a mesh (publish ledger totals, prediction ranks and observed edges to the other replicas, and forward an issue mutation to the leader), a prediction source, a notifier (carries an observation to the notification router) and a tenant listener (told when a tenant's graph loads, unloads or replays), together with the cell store and the job scheduler. A port left out is the single-replica default: always the leader, no mesh, no notifier. There are no setters.

Periodic work is a table of named jobs run by one scheduler (section 6).

Two kinds of decision run side by side. The event path is deterministic code driven by policy, the service graph and recorded patterns, with one decision model for typed questions; it runs on every event. The reasoning loops are model passes that run a few times a day per tenant and write what the event path reads next. No model opens an issue.

Workspaces and tenants

A tenant is the unit of isolation: its own service graph, events, issues, memory, goals, notification channels, budgets and agents. People see a tenant as a workspace. Every event, cell, frame and API row carries a tenant, and every read and write is checked against what the caller may do on that tenant.

Tenants come from one of two places. With tenants.registry on, the registry cell is the source and the API creates and edits them. With it off, a tenant exists when a service-graph cell for it is applied. In both cases there is no default tenant and no static tenant flag; write ingress fails closed until a tenant exists.

Isolation in memory

A cell is visible to every tenant when it carries the shared tag and to one tenant when it carries tenant/<name>. An untagged cell of a tenant-scoped kind resolves to no tenant on a multi-tenant instance and is not served. The rule is applied on the model-facing paths, on the REST surface and on MCP, and a caller who is not an admin cannot write a tenant/, shared or author/ tag. Private cells are a separate rule, described in section 5.

Screening

A regex pre-screen for prompt injection runs on every event. A human-source match is dropped. A machine-source match increments a counter and is logged, and the event is never dropped on the regex. Human events then go to the guardrail model, on by default (pipeline.guardrail in policy), which labels each INFRA, NOISE or INJECTION; an error or an empty answer drops the event (fail closed). The model judges each human event itself; no verdict is cached. With the decision model on, its human-guardrail label is applied as well, and NOISE and INJECTION end the event. Machine events never reach a guardrail model.

Event text that reaches a prompt is wrapped as untrusted data between per-call random fences with an instruction not to follow it.

04

Issue lifecycle

An issue (a concern in the code) is the unit a person acts on: a service, a severity, a summary, the events behind it, a cause and the patterns that bear on it. Its status is new, investigating or resolved. Figure 2 shows the path from an event to an issue.

Allocation and the ledger

The service graph decides which service and instance an event belongs to. It never decides whether the event matters: noise means unallocated, an event no graph node takes, and it opens nothing. An allocated event is never dropped for its tier, its dependents or its blast radius. Every error-bearing event is credited to its service instance in the service ledger by signal family: level, request, log, resource, pod and provider. A row keeps 60 one-minute and 288 five-minute slots, rows are capped at 2,000 per tenant, and the least recently credited row goes first. The ledger answers the question "why did Triage say nothing" and feeds the situation frame, the tenant ledger endpoint and the MCP tools inspect_service and get_tenant_situation.

Openers

An issue opens on evidence that something happened to a service, never on blast radius. These are the only openers; each is code, and a model takes no part in the decision.

Pod-family events (BackOff, Unhealthy, Failed, FailedScheduling and the rest of the pod-failure role) are one instance fact and never open an issue by themselves. A crash loop opens through O1, a second family through O2, and a probe that keeps failing on a Ready workload through O3.

An issue belongs to one workspace. Its id is made of the whole source, the workspace and a timestamp, and every match of an event to an existing issue (attaching to an open one, the recovery fast path, the chronic collapse, the evidence RSI reads) requires the same workspace. A second workspace that emits the same source never attaches to, resolves or reopens the first one's issue. One opener of a source runs at a time on a replica, and an open whose write fails opens nothing and releases its own claim, so the next event of the source opens the issue.

Severity

The band comes from blast radius, the share of the catalog that depends on the service. At or above the tenant's INCIDENT threshold an issue is critical; between the NOISE and INCIDENT thresholds it is warning; below the NOISE threshold, for a leaf, or for a noise-tier node it is info. Evidence raises an info issue to warning and never to critical. A provider-critical event keeps critical. Each channel's minimum severity decides who is paged.

With the decision model on, one score question on the ordered scale info, warning, critical is asked per new issue, from evidence only (the change, what was already said in the last 24 hours, the service's place in the graph, its seven-day issues, its situation line and its ledger families in the last 10 minutes). The issue takes the engine's severity moved at most one step toward the answer. A failing or absent model leaves the engine's severity.

Author pass

After every machine open, one model pass rewrites the engine's templated summary into words an on-call engineer reads in five seconds and, with link_concerns, draws caused-by and duplicate-of edges to the tenant's other active issues. The write is its own mutation kind and does not move the issue's LastSeen, since words are not evidence.

Memory

Memory is one substrate. Every cell is an xray.triageagent.dev/v1 MemoryCell with a kind, a subject (the producing instance), tags, an origin, links to other cells and an optional embedding. The core watches the cells in its namespace whose subject matches its memory subject (memorySubject in the deployment file). Embeddings come from text-embedding-005 on Vertex AI, or from a gateway or sidecar (nomic-embed-text, 256 dimensions); an HNSW index serves similarity search.

Prompt cells

The five prompt cells (triage-system-prompt, triage-routing-prompt, triage-reflection-prompt, triage-reasoning-prompt, triage-voice-prompt) and the per-prompt overrides (triage-prompt-<id>) change only by Helm or a cell apply. No write path of the core touches one, whoever asks and whatever the grant: the memory tools (upsert_memory_item, supersede_memory_item, expire_memory_item, refute_memory_item, consolidate_memory), a model's reflection ops, pattern proposals, voice and chat tools, the cell writer, the sweep that mirrors the store into cells, the janitor and the purger refuse an id that names one, and the REST API has no route that writes a memory item. A prompt cell that carries a tenant or author tag is ignored when the prompt is resolved. The rule is one predicate (prompts.IsCellID) applied where an id enters the memory store (PromptCellRefusal) and where a cell reaches the cluster (store.Cells), with a test for each surface.

Provenance

Every cell has an origin: observed (code wrote it from facts), derived (a model wrote it), human (an identified user wrote it through MCP, chat or voice) or verified (derived, then passed a check in section 6). A cell without an origin is derived. Prompts receive the origin on every cell with one rule: human outranks derived, and a derived cell is a prior claim, never evidence. Code enforces the rule where a model chooses what to rely on: an id accepted as a pattern or a basis must be observed or human.

Visibility

A cell is either tenant-shared or private. A shared cell carries its tenant as the tag tenant/<name>, or the tag shared to be visible to every tenant. It is readable by any caller who holds the read grant on that tenant: the grant is resolved at the API, MCP, voice and room boundary, which hands the memory code only the resolved tenant name. On a multi-tenant instance an untagged cell of a tenant-scoped kind is visible to nobody, and an untagged knowledge cell only to a caller who sees all tenants. A private cell has scope: private and the tag user:<hash>, where the hash is the first 16 hex characters of the SHA-256 of the signed-in person's provider identity (github:<numeric id>, or the OIDC prefix and lower-cased subject). The tag is the only place an owner lives; the subject of a cell names the producing instance. A private cell is visible to that exact hash and to no one else, with no administrator or tenant bypass. It is never embedded, never a search candidate, never a link or traversal target. The REST API and Tria show it to its owner only, and MCP treats it as absent for everyone. The hash is an identifier, not a credential: nothing lists hashes, and what protects a private cell is the session that produces the hash. A memory write through MCP (upsert_memory_item, supersede_memory_item) by a caller who is not an administrator is refused when it asks for scope: private, and every user: tag is stripped from it with the tenant and shared tags; a private note is written only on the owner-bound path (save_session_note). The last-session note enters the system prompt as a fenced block under a line that says to read it as data.

A cell that a caller authors goes through one write path, whether it comes from the MCP memory tools, a voice note or linked pattern, or a pattern a person or the loop approves. How cells are applied

Configuration cells carry their document as base64 bytes under spec.data. The reconciler decodes the document with strict field checking and then a validator. A rejected document keeps the previous good state, so a typo never replaces a working configuration. Every cell write goes through one function of the store: it reads the cell, asks the caller to build the spec from what is stored, and sends a write only when the result differs. Times are compared to the second, the embedding the reconciler wrote is kept, labels are merged onto the cell's own, and a record stored as an encoded blob is compared as a record, since the encoding of a map is not stable. A version conflict re-reads from the API server and builds again. A service graph is either inline (gzip of a gob, decoded under a 64 MiB bound with a panic-to-error guard) or a digest-pinned OCI reference; a tag-only reference is refused and a failed pull keeps the loaded graph.

06

Reasoning loops

The loops are the slow half of the core. A deterministic situation frame describes each tenant; reflection and knowledge passes read the frame and memory and write what the event path reads next; RSI tunes the knobs and the patterns from the outcomes people confirm. Figure 3 shows the loop.

Jobs

Every periodic task of the core is a job in one scheduler: a name, a function, a cadence and two flags, leader-only and singleton. The scheduler owns the timer, the leader gate (a leader-only job skips its timed runs on a replica without the lease), the guard against overlapping runs (a singleton drops a manual trigger that arrives while it runs), panic recovery and each job's status. A cadence that comes from policy is read before every wait, and a policy change pokes the loop jobs, so a new interval applies at the next fire without a restart. A job can hold back until the service graph is ready, and may run once at start.

A run reports a result: the tenants it looked at, the model and tokens it used, the counts it changed and a note. A run that did nothing reports why, for example that no model is configured or that the daily budget is spent. Having nothing to do is not a skip. A tenant over its reflection budget is not woken: the shield leaves its waiting changes until the budget has room, because a pass for it would call no model and hand the changes back to be woken again.

Situation frame

The frame is built without a model from the graph, the RED and USE snapshots, the signals ring, the event cells, the classifier's matches and the ledger. It has one entry per notable service, each with its facts, how long they have held and a one-word reason, capped at situation.maxServices (12). A service is notable when it is not Ready; when memory has stood above the floor (85 percent of its limit) for the hold (30 minutes); when OOM kills are increasing; when log, request or resource anomalies appear in more than streamWindows (5) windows of the last hour; when the error rate is above its floor (5 percent); when an issue is older than the stale age (12 hours) with no level evidence; when more than one issue is open on a service; or when a catalog node's workload names never matched. It also lists sharedMatches, the graph nodes that the anomaly text of two or more other services matched. The frame is served at GET /v2/tenants/{tenant}/situation and by get_tenant_situation, and it wakes reflection when it changes, at most every wakeEvery (10 minutes) and wakeCooldown (30 minutes).

The core describes its own dependencies the way it describes a tenant's. A ledger of self-signals records, for the decision model, the reasoning model and the embedder, the last error with its status, the failures in the last hour and the last success. It appears in every frame, in the RCA brief when the issue's service is the core, and in get_triage_agent_status.

Verified reasoning

A derived claim is checked before it is trusted. With loops.verify on, a fact's cause is tested against live evidence, with at most 3 checks per cause and 500 a day and a minimum support of 0.6. A fact whose cause cannot be tested is demoted to a hypothesis, which expires; a fact that passes becomes verified. Edges in the observed graph carry a role, request, telemetry or control, taken from the destination port, the protocol and a policy list of telemetry-sink names. A telemetry edge stays in the graph for provenance but is not a dependency: blast radius, the dependency layer, the classifier's "Depends on" line and the RCA call path never see it.

Predictions

A precursor matcher raises candidate services from the sequences that preceded past issues (predictions.window 14 days, precisionWeighting on). Each candidate is ranked by the decision model (how likely an issue is within the hour, from its evidence), and the answer becomes the prediction's confidence. An elevated prediction needs a confidence of 0.5; a notification needs 0.8 and re-arms after the confidence falls below 0.5.

Patterns and RSI

A pattern is an operational_pattern cell: a state of one service that people recorded as expected, such as a nightly scale-down, with an optional window. It holds machine opens (section 4), is linked to the issues it explains, and is the base of knowledge: the knowledge pass writes the fact behind it. RSI (recursive self-improvement) reads the outcomes the core can measure and proposes changes. It is off by default.

Earlier waiting proposals are decided too, oldest first

The gates are a consistency streak (applyAfter, 2 passes), the applyTenants list, one applied change per tenant per day, an evaluator that reverts a change that did not improve its objective by minImprovement (0.2) over the evaluation window (6 hours), and the operator's own settings, which win field by field over the RSI overlay. The loop runs every 30 minutes, and a burst of alerts (wakeAlertsPerHour, 6) wakes it with a 30-minute cooldown. The knobs are registered with their bounds: the flap gate, the alert repeat interval and the like.

The pattern track has three parts. New: from one issue a person resolved with a verdict or a root cause, or a flap the machine closed after at least minReopens reopens with nobody's verdict, it drafts a pattern. Revise: when an issue opened on a service after its pattern was recorded and a person resolved it as expected or noise, the reasoning model reads the pattern and the misses and answers with the text or window that would have held them, or with nothing. Retire: a derived pattern that explains nothing is pruned. People see all of it: list_patterns and the memory explorer show the author tag rsi, the status block counts decided and pending proposals, and refute_memory_item, expire_memory_item and approve_pattern remain for a person who disagrees.

The ledger

Every number the core counts is a named counter in one store, the ledger. A counter belongs to a tenant where the number does and otherwise to the whole core. The tenant counters cover the events and issues of the tenant, what the shield did with them, and the model calls and tokens the tenant caused (llm.calls, llm.tokens, llm.prompt_tokens, llm.completion_tokens). And each person's lifetime totals in a member ledger. A counter is added with one line at the place that counts it.

Every replica keeps its own running totals, sends them to the others and sums what it receives, so any replica answers with the mesh-wide number. The totals persist in the system-configuration cell: the flush job (section 6) writes what changed, merging each blob with what the cell holds because every replica flushes to it, and a starting replica seeds from the cell once. A counter is lifetime unless its name says today. GET /v2/agent/status and GET /v2/memory/metrics read these counters.

The counters leave as OpenTelemetry metrics. One observable counter, triageagent_counter, reports the ledger at each collection, with the attributes tenant (empty for the whole core) and counter (the name). No code path records to OpenTelemetry itself, so the exported number and the one the API serves are the same number. Export is on by default (otelTracing.enabled) and idle until an endpoint is set: with none, the providers are no-ops, nothing is logged above debug and no error is raised. The same exporter carries traces.

Agents and joining

An agent opens a WebSocket to /events/ws and proves who it is in the first frame. The HTTP request is upgraded without a credential and authenticated in-band; the first frame has a 90-second deadline and an 8 MiB read limit, and a same-origin check admits requests that carry no Origin. Authentication is the join certificate and nothing else. A hello without a certificate is refused.

Certificate join

  • Joining is enabled when the agent CA is configured (clusterAgents.join.caSecret). The CA is Ed25519; a previous CA can be set for rotation and cross-signs the current one.
  • The core sends a challenge nonce first. The agent's join, renew or hello frame signs it, and the agent verifies the core's CA signature over the same nonce.
  • A CSR carries the cluster name and the tenant list. It is issued only when an approved agent with the same fingerprint and tenant list exists. Certificates last 24 hours (clusterAgents.certValidity), a certificate issued before the latest approval is refused, and revoking, replacing or approving an agent again closes its live sessions on every replica.
  • A request that is not yet approved waits in a pending list (100 entries, 5 per source, 5 per cluster, 24-hour TTL; one source may hold at most a quarter of the queue's size). An admin approves, denies or revokes through /v2/agents and can set an agent's own daily event cap; the owner or admin of a workspace does the same for the agents that serve only workspaces they manage, and sees the list and the requests narrowed to those workspaces.
  • Join attempts are throttled per presented identity (6 a minute) and per source (60 a minute). The source is the peer address, or the Nth X-Forwarded-For entry from the right when trustedProxyHops is N.

One-time keys

A workspace manager mints a key (tak_<id>_<secret>, 256 bits of secret, only its SHA-256 stored) that lasts seven days and is spent by the first successful join. Kinds: cluster (several tenants), host (one tenant, a Linux host) and otlp (one tenant, no Kubernetes watch) and spot (one workspace and one spot, section 11). The join frame carries the key, a CSR and an Ed25519 proof over the nonce; the CSR's cluster name and tenant list must equal the key's, the certificate is issued at once, and the core assigns the cluster name (the label plus an eight-character suffix). The API returns the install command: a Helm line with core.host, core.caFingerprint, core.clusterName, core.tenants and core.agentKey, or for a host the install.sh line.

POST /v2/tenants/{id}/keys takes {label, kind, namespaces, bindings} (label 1 to 63 characters; kind defaults to cluster; bindings replaces the single binding to {id} and must include it) and answers 201 with {key, keyInfo, caFingerprint, install}. key is the wire key, shown once; keyInfo is {id, label, cluster, kind, bindings, createdAt, createdBy, expiresAt}; caFingerprint is the SHA256: fingerprint of the core's CA, which the joining side pins; install maps helm and annotate (cluster), helm and senders (otlp), linux (host) or spot (spot) to the command text. Minting needs write and exec on every tenant the key binds (403 otherwise, the same answer for an unknown tenant); a bad kind, label or binding is 400, no free licence 402, an inactive workspace 404. GET /v2/tenants/{id}/keys lists the unused keys without their secret hash, and DELETE /v2/tenants/{id}/keys/{keyId} revokes one.

Bindings

A key-joined agent holds one binding per tenant, each with an optional namespace list (* or empty means all). The receiver filters snapshot, delta, event, log, RED, USE and topology frames to the binding's namespaces and drops frames for tenants outside the bindings. Heartbeat and sensor-state frames are not tenant-filtered, but each OTLP source entry in a sensor-state frame carries a tenant stamp that is checked against the bindings. A sensor-state frame also carries intake, one entry per OTLP sender the agent receives from: sender, window (seconds the counters cover), exports, points, unread, refused (points), refusedExports (exports refused before decoding), held, sources and unreadByName (at most 20 metric names with their points, most first); a frame is cut to 100 senders, names to 200 bytes, and a negative counter reads as 0. The core keeps it with the rest of the sensor state, gossips it to the other replicas and serves it as sensors.intake on the sessions of clusterAgentStats in GET /v2/agent/status. A sender is not a tenant, so the intake shows on the owning session's row and never on a tenant's row of a cluster-mode agent, and not on the row of an agent whose certificate serves more than one tenant. An agent that sends none has no intake key. Bindings change through POST /v2/agents/{cluster}/bindings: replace the namespaces of one, add a tenant the caller manages, or file a request that the other tenant's managers answer (7-day TTL, 1,000 requests globally). An agent with no binding left is revoked, and deleting a tenant ends its bindings and unused keys at once.

  • REST and WebSockets resolve grants once per request (captured at upgrade for sockets). A ?tenant= route answers 403 for a name the caller cannot read, whether or not it exists; an unknown name is listed back only to a caller who could read some tenant of that name.

Rejected credentials

One guard stands in front of every bearer-authenticated surface: the API port (/v2, /mcp and the WebSocket upgrades), the MCP port and the events port. The credential is the Authorization: Bearer token or, on a WebSocket upgrade, the token in Sec-WebSocket-Protocol. A request that authenticates, and one that presents no bearer credential, never counts.

  • Each 401 answering a bearer credential is charged to the request's source and to the token (its SHA-256), a token bucket each: auth.failureBurst rejections (10), then one more per auth.failureRefill (1 second). The source is the peer address, or the Nth X-Forwarded-For entry from the right when trustedProxyHops is N; an IPv6 source counts as its /64. The tables are bounded (10,000 sources and tokens, 4,096 remembered tokens) and drop their least recently used entry when full.
  • Past the limit of either, the answer is 429 {"error":"too many rejected credentials"} with Retry-After (seconds until the next rejection is given back) and Connection: close, in place of the 401 and its challenge. A bucket that has refilled to half its burst ends the run of refusals.
  • A source or token that stays over its limit for a minute is cut off for auth.failureCutoff (5 minutes; 0 means no cutoff). A token in cutoff is answered 429 before any handler runs. A source in cutoff has every rejected credential answered 429 but the handler still checks it, so a credential that authenticates still passes: a valid client that shares the address is never refused. When the cutoff ends the bucket starts full. auth.failureBurst 0 turns the limit off.
  • The MCP server remembers a spot or OAuth token it rejected, and TokenReview a ServiceAccount token it refused (on every port), for a minute. Session and device tokens on /v2 and static tokens on the events port are table lookups and are not remembered. The same bytes are then answered 401 from memory, with no TokenReview, no signature check and no validator call. A token that could not be judged (the cluster call failed) is not remembered. The TokenReview is limited per source to auth.reviewPerSource reviews a second (50, burst twice that; 0 means no limit) and for the process to 50 (burst 100). A review that is not made, because a limit refused it or the cluster call failed, says nothing about the token: it is answered 503 with Retry-After, never 401, so no bucket is charged, no token is cut off and nothing is remembered.
  • The warnings "invalid MCP token", "TokenReview: not authenticated" and "events: invalid token" are written once per source and kind a minute, with the source and the number suppressed since the last.
  • The ledger counts auth.failures (every rejected bearer credential), auth.throttled (answered 429), auth.cutoffs and auth.logs_suppressed. GET /v2/agent/status shows them to a caller who reads all tenants as auth, with cutSources and cutTokens, the sources and tokens in cutoff on the replica that answered.

MCP OAuth server

When server.publicURL is set and an SSO provider exists, the core is its own OAuth 2.1 authorization server for MCP clients, co-located on port 8080: protected-resource and authorization-server metadata, dynamic client registration restricted to loopback and custom-scheme redirects, PKCE S256 required, a resource indicator that must match, single-use authorization codes that last two minutes, and an EdDSA token whose signing key derives from the configured client secrets so replicas agree. Tokens carry a scope, triageagent:mcp.read or triageagent:mcp.write, and either a grants string or an RBAC subject whose grants are read from the cache on every request. A shorter lifetime for write tokens can be set. Authorization codes live in one pod, so several replicas need session affinity for this flow.

Auth is a bearer token or a named header whose value is read, per call, from the Secret the entry names through the Kubernetes API in the core's namespace; nothing is passed through environment or arguments. Tria reaches a server through list_available_tools and call_mcp_tool with a server name, a tool name and parameters. A non-empty allowlist is the whole surface of the server: its tools are listed without a probe, only they are named in the session context, and a call to any other tool is refused before it reaches the server. With no allowlist every tool the server offers is listed, found by a probe that sends the server's credential. The same list builds the event agent's toolset, filtered by the same allowlist; the agent probes each server at start and skips an unreachable one.

An entry may carry a sender, the id this core's spans carry on the server. Every call_mcp_tool call to such a server then carries the argument tenant = <sender>/<workspace id>, the workspace the chat or voice session is bound to, overriding whatever the model wrote there; a session bound to no workspace is refused. A server with a sender is per person: it serves chat and voice only, the event agent builds no toolset from it, and the health checks still probe it.

A call to a server with an allowlist runs without a confirm in the private chat and in voice, because the operator who wrote the entry named those tools. A call to a server without one asks in the chat. A room answer calls an external server the same way: the room's workspace is the tenant of the call (the core sends it as the tenant argument, sender/workspace; an allowlisted server whose entry has no sender is refused, never called unbound), a server with an allowlist runs without a confirm, and a call to a server without one is declined, because a room cannot ask.

Notifications

One component, the interrupt shield, decides everything a channel hears. The engine only offers a candidate: a new issue, a resolved issue, a prediction crossing or an observation. The shield sets a new issue's severity with the decision model (section 4), queues the change for its tenant, and lets reflection write the message in its next pass. A new issue wakes a scoped reflection pass at most once per tenant every 10 minutes; changes that arrive meanwhile ride in the same pass, and recoveries, risk crossings and observations never wake one.

  • A new issue that is critical once its severity is set is sent at once, verbatim.
  • A repeat gate suppresses the same (kind, tenant, service) inside alerts.repeatInterval (1 hour, bounds 0 to 24 hours). Critical is never suppressed. RSI tunes this knob.
  • With the decision model's gate switch on, a non-critical issue that outlives the blip window reaches reflection only above 0.5.

Observations

When memory notices something before anything is down, such as a service that has held 95 percent of its memory limit for six hours, the reflection write emits an observation. It goes through the same router and the same channel floors, leader-gated, with a minimum interval between them.

FAQ

Why does a service nobody depends on still get an issue?

Blast radius sets severity; the evidence decides whether anything happened. A leaf service that goes degraded opens an info issue through the level state, and corroboration can raise it to warning, never to critical. Whether anyone is paged is a property of each channel's minimum severity, which defaults to warning. A leaf that should stay silent belongs in a quiet scope or under a recorded pattern.

Why does a lone BackOff or Unhealthy event open nothing?

A pod-family event is one fact about an instance. It is counted and shown in the frame, and an open issue on the service absorbs it. A crash loop reaches the level state and opens through O1 within a minute, a second error family opens through O2, and a probe that keeps failing on a Ready workload opens through O3 after the dwell. A flapping probe on a workload that stays Ready opens nothing.

What happens when the decision model or the reasoning model is down?

The event path goes on. Without the decision model the engine keeps its own severity, the machine open is not judged against patterns, a human message passes on the regex alone, and predictions use the matcher's score. Without the reasoning model the loops do not run: no new reflection, knowledge or RSI output, while everything already written stays in force. Each dependency's failure count and last success appear in the situation frame, and a burst of decision-model failures raises one event on the core's own service, at most every ten minutes, when that service is in a tenant graph. The guardrail model is the exception: on an error it drops the human event.

How do I tell the core that a state is known and fine?

Three ways, from the narrowest. Resolve the issue with the verdict expected (or noise) and a window, which holds machine opens on that service (or source) for up to 30 days. Record a pattern, in one sentence through link_pattern, chat or voice, with an optional schedule; the opener asks the decision model whether a new open is an instance of it. Or set a quiet scope in policy for services that should never open. A human report is never held by any of them.

How does a new cluster or host reach a workspace?

A workspace manager mints a one-time key in the workspace and runs the install command the API returns: a Helm line for a cluster, an install.sh line for a host. The agent sends the key with a CSR and an Ed25519 proof, and the core issues a 24-hour certificate at once and renews it. Without a key, the agent prints its fingerprint and an instance admin approves it. A key is spent by the first successful join and lasts seven days, and the workspace's licence count limits how many agents it can bind.

What leaves the cluster toward a model provider?

Event text, service-graph facts, recent issue lines and the memory a prompt needs, in the roles of section 7. Human messages are screened first, and event and graph text inside a prompt is fenced as untrusted data. A tenant that must not send its text to the decision model turns its own decisions switches off. Embeddings can stay on the pod with the local sidecar, and with the local chat sidecar every model role can too. Token use is bounded by the budgets of section 7 and visible in the status.

What is lost on a restart or a failover?

Nothing durable. Issues, memory, configuration, the registry and the lifetime counters are cells; the counters are flushed every minute. The event hub, the service ledger, the situation frame and the rate limiters are in memory and refill from the agents, which reconnect and resend their snapshots. Corroboration and persistence start from what has arrived since, so a service can take a few minutes to reopen on a fresh pod.
